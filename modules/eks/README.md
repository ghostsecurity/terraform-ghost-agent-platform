# Ghost Agent Platform on Amazon EKS

Terraform module that installs the Ghost Agent Platform into an existing EKS cluster with Ghost's Helm chart, along with the AWS resources it needs: shared storage, AWS identities for its pods, the load balancer, the certificate, and DNS.

For a complete test deployment, cluster included, see [examples/eks](../../examples/eks/README.md).

## What gets deployed

- **A namespace** (`exo` by default) labeled for the `restricted` Pod Security Standard.
- **The platform** as a Helm release of the `exo-helmchart` chart at `exo_version`: gateway, credential proxy, updater, MongoDB, the web UI, and the worker pools. With `manage_release = false` you install the release yourself instead; see [Installing the release yourself](#installing-the-release-yourself).
- **2 EFS file systems** with mount targets, security groups, and daily AWS Backup backups. The private one holds the platform's keys and certificates and accepts NFS only from the control-plane nodes; the shared one holds run artifacts, public certificates, and runner identities. Both are protected with `prevent_destroy`.
- **3 storage classes**: one per EFS file system (access points owned by uid/gid 65532) and a gp3 EBS class for MongoDB, all with the `Retain` reclaim policy.
- **An Ingress** for the AWS Load Balancer Controller: an Application Load Balancer that redirects HTTP to HTTPS, uses a TLS 1.3 security policy, accepts only `ingress_cidrs`, and keeps WebSockets open for an hour.
- **(Optional) An ACM certificate** validated through DNS, and **a Route 53 alias record** for `domain_name`, when `route53_zone_id` is set. The record, like the Ingress, only with `manage_release`.
- **AWS identities through EKS Pod Identity**: the updater can read the release tags of Ghost's `exo-stack` repository, to report new versions; with `enable_ses_email`, the gateway can send email through SES. No other pod gets an AWS identity.
- **The credential encryption key**, generated by Terraform and stored in Secrets Manager and in a Kubernetes Secret, and **the one-time claim token** for the setup wizard.
- **(Optional, on by default) Ghost support access**: a role Ghost Security assumes to reach the UI and read the platform's logs over Session Manager. See [Ghost support access](#ghost-support-access).

## Cluster prerequisites

The module does not install cluster components. The cluster needs:

- **Kubernetes 1.29 or later, IPv4.**
- **Network policy enforcement**: the Amazon VPC CNI add-on with `enableNetworkPolicy` set to `"true"`. Workers run agent-driven code and reach the internet only through the credential proxy; network policies are what enforce that.
- **The EKS Pod Identity Agent add-on.**
- **The EBS CSI driver and the EFS CSI driver add-ons**, each with an IAM role. The EFS driver creates an access point per volume.
- **The AWS Load Balancer Controller**, and subnets tagged for it: `kubernetes.io/role/elb` on public subnets (or `kubernetes.io/role/internal-elb` on private ones for `internal_load_balancer`).
- **Separate nodes for the control plane and the workers.** Workers never share a node with the gateway, credential proxy, updater, or database. Give the control-plane nodes a security group that no other node carries (`control_plane_node_security_group_ids`) and a label (`control_plane_node_selector`). A tainted node group for the workers (`worker_node_selector`, `worker_tolerations`) keeps everything else off them.
- **Pod traffic between nodes** allowed by the node security groups: TCP 8000, 8001, 8053, 8080, 8443, 8444, and 27017, and UDP 8053. The EKS community module's recommended node rules cover the TCP ports; add UDP 8053.
- **Image pulls from Ghost's registry**: the AWS account is on Ghost's allowed list (see [Onboarding](../../README.md#onboarding)), and the node role can pull from ECR (`AmazonEC2ContainerRegistryReadOnly`, attached to EKS managed node groups by default).
- **Node disks** of at least 50 GiB on control-plane nodes and 100 GiB on worker nodes. See [Sizing](#sizing).
- **For Ghost support access**: `AmazonSSMManagedInstanceCore` on the control-plane nodes' role, so Session Manager can reach them, and the cluster's private API endpoint enabled. Leave it off the worker nodes.

Requiring IMDSv2 with a hop limit of 1 on the nodes is recommended, so pods cannot reach the instance metadata service.

## Usage

The module uses the caller's `aws`, `kubernetes`, and `helm` providers. The Helm provider must be logged in to Ghost's registry, which serves the chart:

```hcl
data "aws_eks_cluster" "this" {
  name = "my-cluster"
}

data "aws_ecr_authorization_token" "ghost" {
  registry_id = "052783882429"
  region      = "us-east-1"
}

provider "helm" {
  kubernetes = {
    host                   = data.aws_eks_cluster.this.endpoint
    cluster_ca_certificate = base64decode(data.aws_eks_cluster.this.certificate_authority[0].data)
    exec = {
      api_version = "client.authentication.k8s.io/v1beta1"
      command     = "aws"
      args        = ["eks", "get-token", "--cluster-name", "my-cluster", "--region", "us-east-1"]
    }
  }

  registries = [{
    url      = "oci://052783882429.dkr.ecr.us-east-1.amazonaws.com"
    username = data.aws_ecr_authorization_token.ghost.user_name
    password = data.aws_ecr_authorization_token.ghost.password
  }]
}

module "ghost_agent" {
  source = "github.com/ghostsecurity/terraform-ghost-agent-platform//modules/eks?ref=<latest release tag>"

  cluster_name    = "my-cluster"
  exo_version     = "v1.2.3"
  domain_name     = "ghost.example.com"
  route53_zone_id = "Z0123456789ABCDEFGHIJ"

  subnet_ids                            = ["subnet-0abc...", "subnet-0def..."]
  node_security_group_ids               = ["sg-0nodes..."]
  control_plane_node_security_group_ids = ["sg-0control..."]

  control_plane_node_selector = { "exo.ghost.security/node-role" = "system" }
  worker_node_selector        = { "exo.ghost.security/node-role" = "worker" }
  worker_tolerations = [{
    key    = "dedicated"
    value  = "exo-worker"
    effect = "NoSchedule"
  }]
}
```

Configure the `kubernetes` provider for the same cluster. The [EKS example](../../examples/eks/main.tf) shows the full provider setup.

Don't put `depends_on` on the module call, for example on the module that creates the cluster. Whenever that dependency changes, such as during a cluster upgrade, Terraform postpones the module's reads of the cluster to apply time and plans changes to everything built from them, the Helm release included. Create the cluster and its add-ons first (the example's first apply step does), and the module needs no explicit ordering.

## After apply

1. Open the `url` output, enter the claim token (`terraform output -raw claim_token`), and create the first admin.
2. Check that workers reach the internet only through the credential proxy:

   ```bash
   aws eks update-kubeconfig --region <region> --name <cluster>
   helm test exo -n exo
   ```

   The `exo-test-worker-isolation` test fails when network policies are not enforced.

Before DNS resolves, `kubectl -n exo port-forward svc/exo-ui 8080:8080` reaches the UI at `http://localhost:8080`.

The domain, TLS, worker pools, and email come from this module. The UI shows them read-only under System > Instance; change them here.

## Upgrading the platform

Set `exo_version` to the new release and apply. The UI announces new versions with a `helm upgrade` command; with this module, change `exo_version` instead, since Terraform would revert an upgrade made outside it.

The gateway and credential proxy are replaced rather than rolled, so the platform is briefly unavailable and runs in progress stop. Upgrade when no runs are active.

## Upgrading the cluster

The platform keeps running through a Kubernetes version upgrade of the cluster, but each node group replaces its nodes, and every pod moves:

- **Upgrade when no runs are active**, one minor version at a time. The gateway, credential proxy, and database each restart once on a new node, so the platform is unavailable for a few minutes, and a run on a worker that is moved stops.
- **Keep NFS access to the EFS file systems intact throughout.** A pod has to unmount its volumes before its node can be drained. If the nodes lose NFS access mid-upgrade, pods hang in `Terminating`, and after about 15 minutes EKS abandons the node group update with `PodEvictionFailure` and keeps the old nodes. So don't change the node security groups, or anything this module builds its security group rules from, in the same apply as the version change.
- **Keep a control-plane node in every availability zone** the node group spans. MongoDB's EBS volume belongs to one zone, so the database can only restart on a node in that zone. It takes a minute or two after moving to accept connections again, and the gateway and credential proxy wait for it.

With the EKS community module, node groups follow the cluster version: change it and apply, and Terraform upgrades the control plane, then the node groups, then the add-ons. Afterwards, check that every node reports the new version (`kubectl get nodes`), that every pod in the namespace is ready (`kubectl -n exo get pods`), and that `helm test exo -n exo` passes.

## Installing the release yourself

To manage the platform's Helm release yourself, with Helm or a GitOps tool such as Argo CD, set `manage_release = false`. The module still creates everything else: the namespace, the encryption key and claim token Secrets, EFS and the storage classes, the AWS identities, the certificate, and Ghost support access. It creates no Helm release, Ingress, or DNS record.

The `helm_values` output holds the values that connect the release to those resources: storage classes, Secrets, fixed Service addresses, node placement, and email. Install the chart with them into the module's namespace, adding ingress values of your own. Expose the outputs in your configuration first:

```hcl
output "exo_helm_values" {
  value = module.ghost_agent.helm_values
}

output "exo_certificate_arn" {
  value = module.ghost_agent.certificate_arn
}
```

```bash
terraform output -raw exo_helm_values > exo-values.yaml
helm install exo oci://052783882429.dkr.ecr.us-east-1.amazonaws.com/exo-helmchart --version 1.2.3 \
  -n exo -f exo-values.yaml -f ingress-values.yaml
```

For example, an `ingress-values.yaml` for the AWS Load Balancer Controller:

```yaml
ingress:
  enabled: true
  className: alb
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS": 443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    alb.ingress.kubernetes.io/certificate-arn: <the exo_certificate_arn output>
    alb.ingress.kubernetes.io/ssl-policy: ELBSecurityPolicy-TLS13-1-2-2021-06
    alb.ingress.kubernetes.io/load-balancer-attributes: idle_timeout.timeout_seconds=3600
```

Then point `domain_name` at the load balancer.

- **Keep the values in every install and upgrade.** They set the fixed Service addresses, which cannot change once the Services exist. Upgrade with `helm upgrade ... --reset-then-reuse-values`, or with your GitOps tool, which keeps them as part of the application.
- **They work under `helm template` and GitOps tools,** because they spell out what the chart would otherwise look up in the cluster: the Service addresses, and the claim token Secret.
- **`exo_version`** then only sets the version in the `helm_chart` output. The release runs whatever version you install.

## Worker pools

Each entry in `worker_pools` runs its own Deployment of workers. A worker pod runs one agent run and is then replaced, so `replicas` is the number of runs a pool handles at once.

```hcl
worker_pools = [
  { name = "default", replicas = 4 },
  {
    name         = "lint"
    replicas     = 1
    image        = "123456789012.dkr.ecr.us-east-1.amazonaws.com/exo-worker-lint:1.2.3"
    capabilities = ["shellcheck", "hadolint"]
  },
]
```

A pool without an `image` runs the published worker image. For a pool with extra tools, open System > Worker add-ons in the UI and choose Create worker image: it produces a Dockerfile based on the published worker image and the command to build it. Rebuild custom images with `--build-arg EXO_VERSION=<new version>` before each upgrade so their worker runtime matches the platform. The nodes must be able to pull the image.

## Sizing

### Node disks

Container images and every pod's scratch space live on the node's root disk. The kubelet deletes unused images once a disk is 85% full, so images left behind by upgrades clean themselves up.

- **Control-plane nodes: 50 GiB.** Their images are small, and MongoDB's data is on its own volume.
- **Worker nodes: 100 GiB or more.** A worker image is roughly 4 to 6 GB, and during an upgrade a node can hold the current and previous image of each pool. Each worker pod also requests 10 GiB of scratch space and may use up to 50 GiB. Scratch space lasts one run: the worker pod is replaced after each run, and its files go with it. Pods are scheduled by what they request, so a few runs that use far more than 10 GiB can fill a disk; the kubelet then evicts a worker and its run fails. For heavy runs, size worker disks for twice the pool images plus the scratch space of the runs a node holds at once, or lower the limit:

  ```hcl
  extra_helm_values = [yamlencode({
    workers = { resources = { limits = { "ephemeral-storage" = "30Gi" } } }
  })]
  ```

### Database volume

MongoDB's volume is 100 GiB unless set otherwise at install. Run history and audit rows are kept until deleted, so the database grows with use. For a larger start:

```hcl
extra_helm_values = [yamlencode({
  database = { persistence = { size = "250Gi" } }
})]
```

Kubernetes cannot change the volume size of an existing StatefulSet, so changing `database.persistence.size` after install makes the upgrade fail. Leave the value as it was and grow the volume's claim instead. The module's storage class allows expansion, and EBS grows the volume while MongoDB runs:

```bash
kubectl -n exo patch pvc data-database-0 \
  -p '{"spec":{"resources":{"requests":{"storage":"250Gi"}}}}'
kubectl -n exo get pvc data-database-0   # CAPACITY shows the new size when done
```

EBS allows one size change per volume every six hours, and volumes cannot shrink.

### EFS

The file systems have no fixed size: they grow with their data and are billed per GB stored. The volume sizes in the chart's values do not limit them.

## Ghost support access

By default the module publishes a `<name_prefix>-ssm-support` IAM role (output `ghost_support_role_arn`) that Ghost Security assumes for support. Its trust is scoped to a single Ghost support role. Everything it does goes through AWS Systems Manager Session Manager on the cluster's nodes, so it needs no inbound ports and no public cluster endpoint:

- **The UI**: a port-forwarding session to the platform's UI Service. Signing in still needs an account on the instance.
- **Kubernetes, in the platform's namespace only**: a port-forwarding session to the cluster's private API endpoint, with an EKS access entry that can read pods, logs, events, and workloads, and delete pods to restart them. It cannot read Secrets, exec into pods, forward ports to them, or change any workload. Cluster-wide it can read nodes, volumes, and storage classes.

Sessions can use only the two port-forwarding documents the module creates (output `ghost_support_session_documents`), so the role opens no shell on a node and reaches no other destination. It can start sessions only on nodes tagged with this cluster's name that run the Session Manager agent with `AmazonSSMManagedInstanceCore` on their role, which should be the control-plane nodes alone.

To turn it off, set `ghost_support_access_enabled = false`. The role, its access entry, its Kubernetes permissions, and the session documents are removed.

## Email

`enable_ses_email = true` with `email_from` sends password resets and invites through Amazon SES as the gateway's own AWS identity, with no stored password. The SES identity must be verified in `ses_region` (the cluster's region by default), and new SES accounts need production access to reach arbitrary recipients. `ses_identity_arns` restricts which identities the gateway may send as; include the configuration-set ARN too if the account applies a default configuration set.

For SMTP or Resend, create a Secret in the namespace with `EXO_SMTP_PASSWORD` or `RESEND_API_KEY` and pass the chart's email values:

```hcl
extra_helm_values = [yamlencode({
  email = {
    provider       = "smtp"
    from           = "noreply@ghost.example.com"
    smtp           = { host = "smtp.ghost.example.com", username = "ghost" }
    existingSecret = "exo-email"
  }
})]
```

## Data and backups

| Data | Where | Backup |
| --- | --- | --- |
| CA keys, session-signing secret, service certificates | Private EFS file system | AWS Backup, daily (`efs_backup`) |
| Run artifacts and skill files, public certificates, runner identities | Shared EFS file system | AWS Backup, daily (`efs_backup`) |
| Application database | gp3 EBS volume of the `data-database-0` claim | Daily EBS snapshots (`enable_database_snapshots`), or `kubectl -n exo exec database-0 -- mongodump --archive --gzip > exo.archive.gz` |
| Credential encryption key | Secrets Manager (`<name_prefix>/encryption-key`) and the `exo-encryption-key` Secret | Secrets Manager |

Stored credentials cannot be decrypted without the encryption key. To rebuild in another account, copy it from Secrets Manager along with the data.

`enable_database_snapshots = true` creates a Data Lifecycle Manager policy that snapshots the database volume daily, keeping `database_snapshot_retention_days` (30 by default). It finds the volume by its `exo:snapshot-group = <name_prefix>` tag, which the module's storage class sets, so it never touches other volumes. The snapshots are crash-consistent, which MongoDB recovers from on startup. For a central backup policy, leave this off and point your own AWS Backup plan at that tag instead.

The bundled MongoDB does not use authentication. Network policy admits only the gateway and the credential proxy, but it does not cover processes on the cluster's nodes, host-network or privileged pods, or anyone with a shell on a node; any of these can read and write the database, though stored credentials stay encrypted. On a shared cluster, or where your policies require database authentication, use an existing MongoDB replica set with authentication instead: set `database.enabled = false` and `externalDatabase.existingSecret` through `extra_helm_values`.

## Removing

The EFS file systems are protected with `prevent_destroy`, so `terraform destroy` stops before deleting them. Remove the line in this module's `storage.tf` temporarily to tear down a test deployment.

Deleting the namespace releases the volumes, but the `Retain` reclaim policy keeps their data: the database's EBS volume remains in the account (tagged `kubernetes.io/created-for/pvc/name = data-database-0`) until you delete it. Snapshots taken by `enable_database_snapshots` also remain after their policy is removed. The Secrets Manager secret enters a 7-day recovery window.
